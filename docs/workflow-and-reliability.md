# FlowDesk 业务闭环与可靠任务

实现日期：2026-10-04。此文解释当前代码；实际运行范围见 `acceptance.md`。

## 状态与角色

所有操作先检查空间成员有效性，提交人再限制 `creator_id=当前用户`。前端读取 `/tickets/{id}/actions`，可用按钮由后端规则决定。

| 起点 | 终点 | 可操作角色 | 附加条件 |
| --- | --- | --- | --- |
| 新建 | 已受理 | 管理员、处理人员 | 有效负责人 |
| 已受理 | 处理中 | 管理员、处理人员 | 有效负责人 |
| 处理中 | 待验收 | 管理员、处理人员 | 有效负责人 |
| 待验收 | 已关闭 | 创建人或管理员 | 显式确认 |
| 待验收 | 处理中 | 创建人或管理员 | 必填原因、有效负责人 |
| 已关闭 | 处理中 | 创建人或管理员 | 必填原因、有效负责人 |
| 新建 | 已取消 | 创建人或管理员 | 必填原因 |
| 已受理、处理中、待验收 | 已取消 | 管理员 | 必填原因 |

提交人只能编辑自己新建工单的标题、描述，不能调整负责人或优先级。工作人员可以编辑可见工单；取消是终态，关闭后有明确重开操作。评论、附件和历史始终遵循相同可见性。

## F02：一次业务修改的边界

`tickets.save_change` 使用 `UPDATE tickets WHERE id AND workspace_id AND version`，同时递增 version。受影响记录为零返回 409。修改前后快照、操作者和原因写入 `ticket_events`，随后只提交一次事务。历史写入失败时更新一起回滚。

真实并发测试让两个独立 PostgreSQL 连接都读到旧版本，再同时进入条件更新。断言两个数据库进程号不同，恰好一个 200、一个 409，版本只增加 1，事件只有 1 条。另用数据库 CHECK 失败验证创建、修改、流转、评论、附件五种回滚路径。

创建工单接受 `Idempotency-Key`。键限定当前空间和操作者，当前只用于建单，故不引入多操作抽象。规范化参数做 SHA256。PostgreSQL `ON CONFLICT DO NOTHING` 等待并发请求完成；相同参数返回最初的响应快照，不同参数 409。失败事务连同键预留一起撤销。前端同一份表单的网络重试复用键，内容改变则换键；跨刷新不保留键。

## 筛选、聚合与文件

搜索标题或 UUID、状态、优先级、负责人、未分派、创建日期、更新时间排序都在数据库执行。分页附带 UUID 稳定排序；日期采用含时区的半开区间。列表不是当前页本地过滤。看板统计状态、优先级及未完成工单的负责人分布；每列展示最近 20 条，提供全量列表入口。

附件支持 PNG/JPEG/PDF/UTF-8 TXT，最大 5 MiB、每单 10 个。检查文件名、扩展名、基础文件签名或文本编码；不是恶意文件扫描器。附件仅以下载形式返回，`application/octet-stream`、`nosniff`、CSP sandbox；不内联渲染、不暴露静态目录。限量在工单行锁内检查。

**与初始草案的取舍：** 附件二进制存 PostgreSQL，元数据、内容与事件同事务，避免文件系统与事务失配；最多 50 MiB/工单。评论作为不可变活动事件保存，不重复维护评论表。CSV 使用私有持久卷。附件量增长后再迁移对象存储，当前不宣称具备大规模文件存储能力。

## F03：数据库是任务状态的依据

提交导出时，一次事务创建 `jobs`、`outbox_events` 和 `job_events`。API 不直接依赖队列成功，也不在 HTTP 请求中生成 CSV。任务只允许创建者查看、下载和恢复；管理员不会自动获得其他用户的导出。

`dispatcher.py` 是独立周期投递器，不依赖 Redis 中的定时消息来恢复 Redis 故障。每 5 秒扫描。投递前落库记次数、抢占标识和下次时间；成功发送后记录 sent。发送成功但记录前崩溃可能重复投递，因此不承诺严格只执行一次。

| 边界 | 当前值 | 达到边界后的行为 |
| --- | --- | --- |
| 每轮队列投递 | 最多 5 次 | `DELIVERY_EXHAUSTED`，停止自动投递 |
| 每轮执行 | 最多 3 次 | 明确 failed，保存错误码 |
| 投递等待 | 30、60、120、240、480 秒 | 没有 Worker 时也受预算约束 |
| 执行退避 | `5 × 2^本轮执行次数` 秒 | 不清零重试计数 |
| Worker 租约 | 120 秒 | 对账后有限重试 |
| Linux Worker 超时 | 软 90 秒、硬 110 秒 | 中断后由数据库对账恢复 |
| 导出规模 | 10,000 行 | 超限终止，业务错误不自动重试 |
| 导出保存 | 24 小时 | 下载立即拒绝；后台清理文件 |
| 同用户待处理任务 | 最多 5 个 | 新请求 429 |

Worker 使用任务行锁获得随机 claim token。CSV 写入 `{任务ID}.{claim}.tmp`、flush/fsync，完成后再次锁定任务、检查 claim 与租约及权限，才原子替换 `{任务ID}.csv` 并提交 succeeded。旧 Worker 即使稍后恢复，也不能覆盖新 claim 的产物。文件已替换但数据库未提交时，下载仍不可见，后续重试安全覆盖同一任务文件。临时文件与过期结果定期清理，最早 240 秒后清理旧文件。

自动失败不会无限清零预算。人工重试要求任务创建者的有效成员身份与非空原因，generation 增加，本轮计数清零，但累计投递和执行次数继续增加；审计保留每一轮。权限撤回和参数/规模错误直接终止。暂时的文件或数据库操作失败按预算恢复；故障类别不向用户泄漏内部路径或堆栈。

CSV 对以 `= + - @`（包括前导空白）或制表/回车/换行开头的值加单引号，防止表格软件按公式执行。提交记录角色，执行前、发布前、下载时重新检查；角色改变即拒绝旧产物，避免降权后获取先前的全空间导出。

## 集成与限流

集成令牌随机生成，数据库只存 SHA256，明文只在创建响应中显示一次。有效期 1—90 天，可撤销；三个 scope：读取工单、创建工单、评论。scope 与当前角色、当前空间取交集；不能管理成员、签发令牌、导出或推进状态。Bearer 仅在工单路由独立鉴权；无有效 Bearer 时不会因为伪造头而绕过 Cookie/CSRF。

登录限流使用 Redis Lua 原子 INCR+EXPIRE，同时限制真实客户端 IP 和规范化账户的散列，不存明文邮箱。默认每 60 秒 10 次，超限返回 429 和 Retry-After。Redis 故障时登录返回 503（关闭入口），已有会话仍可用。Uvicorn 只在容器私有网络接受 Nginx 转发，Nginx 覆盖客户端伪造的转发头。当前无 Redis 的 Windows 演示 `.env` 明确设为 false；Compose 默认启用。
