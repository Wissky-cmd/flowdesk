# 阶段一实施与学习清单

状态：阶段一已实现并通过对应验收（2026-10-04）。本文件保留设计清单；实际结果见 acceptance.md。后续阶段尚未实施。

## 结构与边界

采用独立 Git 仓库和模块化单体：`backend/app` 下分配置/数据库、账户会话、工作空间、工单模块；`backend/alembic` 存迁移；`backend/tests` 存真实 PostgreSQL 测试；`frontend` 使用 Vue 3 + TypeScript + Vite + Vue Router + Pinia + Element Plus；`docs` 保存设计、学习和验收证据。

后端使用 FastAPI、Pydantic v2、SQLAlchemy 2 异步数据库访问、Alembic、PostgreSQL。准确版本以实际兼容性核验和锁文件为准。第一阶段不引入微服务、支付或 AI 模型调用。

## 账户、权限和数据库

- 服务端会话使用高熵随机令牌，数据库只存哈希；Cookie 配置 HttpOnly、SameSite，生产环境 Secure；明确过期和退出撤销。
- Cookie 写请求检查来源与 CSRF；登录入口也检查来源，避免登录 CSRF。
- 每个工单请求先验证当前有效用户和空间成员关系；成员角色每次读取，撤权后立即生效。
- 管理员管理当前空间成员并查看空间工单；处理人员查看空间工单；提交人只能查看自己创建的工单。越权资源统一返回 404，角色操作限制返回 403。
- 基础表：users、sessions、workspaces、memberships、tickets。邮箱唯一、成员组合唯一、角色/状态/优先级检查约束；工单创建人及负责人通过空间成员组合外键保证归属合法。
- 工单列表使用空间过滤、角色可见性过滤、稳定排序和有界分页；详情查询同时带空间 ID、工单 ID 和可见性条件。
- Alembic 负责建表，不在应用启动时用 create_all 替代迁移。阶段一先保留 version 字段；乐观锁和状态流转在下一阶段验收。

## 页面和种子数据

提供登录、空间切换、工单列表、创建、详情、成员管理页面；覆盖加载、空列表、失败、登录过期与权限不足反馈。前端仅负责交互提示，后端执行最终鉴权。

种子数据包含两个空间、管理员/处理人员/提交人三种角色、同空间另一提交人和仅属于另一空间的用户。只使用虚构账户；开发密码由环境变量或随机生成提供，不写入真实密钥。

## 阶段一验收

1. 在真实 PostgreSQL 上从空库升级迁移、检查迁移与模型一致性，运行种子脚本并验证重复执行行为。
2. 验证密码错误、会话过期、退出后重放旧 Cookie、禁用用户、撤销成员角色，以及 CSRF/Origin 缺失或错误。
3. 三类角色验证工单创建、列表和详情；检查同空间提交人隔离、跨空间读取、伪造负责人以及非管理员成员管理请求。
4. 直接向数据库提交违反唯一、检查和组合外键的记录，断言 PostgreSQL 拒绝。
5. Playwright 使用真实前后端和 PostgreSQL：登录 → 选择空间 → 创建 → 列表 → 详情 → 刷新；另一独立浏览器上下文登录另一空间用户，尝试读取同一工单，断言拒绝。
6. 保存实际命令、环境、Git 提交版本、pytest 报告、Playwright 报告和截图，更新 acceptance.md 后才推进下一阶段。

## 需要理解的关键代码（实现后填写准确路径）

- 正常链路：Vue 表单 → 请求封装/CSRF → FastAPI schema → 会话与空间依赖 → 工单服务 → PostgreSQL 事务提交。
- 失败链路：另一空间用户带合法会话请求工单 → 成员/可见性条件不满足 → 404；不能只在页面隐藏按钮。
- 数据库约束：为什么应用层检查不能代替唯一约束和组合外键；并发请求如何使“先查再写”出现竞态。
